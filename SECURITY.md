## Architecture and data leaving the browser — inspected

- `src/main.js` calls deterministic `src/tipping.js` arithmetic.  Equal and By person calculations run in the browser, using integer cents.  There is no runtime AI or model-provider request.  Codex is a development tool, not a runtime dependency.
- Trips use browser `localStorage`, key `utility-suite.trips.v1`, through `src/trips.js`.  There is no server-hosted database, account system or cloud synchronization.  Creating a trip writes its generated ID and trimmed name.  Explicit saving writes a result ID, trip ID, timestamp, snapshot version, split mode, destination/currency, original subtotal/charges/tip/diner inputs, per-person subtotals when applicable, integer-cent totals, shares and proportional breakdown.  Conversion estimates are not saved.  Invalid/stale results are rejected before writing; success events follow successful storage writes.  Saved records are validated/recalculated on read, copied independently and rendered with textContent rather than interpreting trip names as HTML.
- Conversion sends only `base` and `target` query parameters to `https://jsd10030-utilityapp.onrender.com/api/rates`.  Requests omit browser credentials.  Render calls a fixed `https://api.frankfurter.dev/v2/rate/{base}/{quote}` URL and returns only base, quote, rate and date.  Bill amounts, trip names, snapshots and individual diner inputs stay in the browser.  Exact-cent conversion is performed locally.  There is no direct browser-to-Frankfurter fallback in the current served bundle.
- Hosting/analytics connections also leave the browser: GitHub Pages receives normal page/asset requests; PostHog's loader comes from `https://us-assets.i.posthog.com/static/array.js`, and configured analytics ingestion uses `https://us.i.posthog.com`.  PostHog can fetch additional SDK/replay resources.  Network providers see connection metadata such as IP address and ordinary HTTP/browser metadata; frontend data remaining local is not a claim of complete anonymity.  Clicking guidance or provider source links navigates to those external sites (Brand USA, Visit London, French Economy Ministry, Frankfurter), with normal navigation/referrer behavior.  Render hosting/platform logs and vendor retention/settings were not accessible and are not certified by this audit.

## Backend review and live requests — inspected / HTTP verified

`server/rates.js` accepts only GET `/api/rates` with exactly two query entries, supported base USD/GBP/EUR, target USD/GBP/EUR/HKD, and different currencies.  Extra/duplicate parameters, unsupported currencies and request bodies are rejected.  The upstream URL is a fixed HTTPS prefix with allowlisted currency segments; redirects are disabled.  An 8-second deadline covers fetch and JSON reading.  Returned currencies, finite positive numeric rate and a valid non-future UTC rate date are checked before sending allowlisted response fields.  The browser has its own 10-second timeout and stale-request/cancellation protection.  Current errors return simple JSON with 400/403/404/405/429/502/504 statuses; upstream response bodies/private error details are not echoed.  Cache-Control is no-store.

CORS allows the configured single Pages origin when an Origin header is present.  A request without Origin can still use the API, including the local Vite proxy.  Missing ALLOWED_ORIGIN would disable cross-origin browser readability rather than authenticate access.  `/health` bypasses rate fetching and returns process liveness only.  The only application console log is startup host/port; no request, bill, trip or credential logging is implemented.  Infrastructure logs were not inspected.

Exactly three ordinary read-only Render requests were made for this audit; no malformed-origin/attack probes, broad scans, rate/load tests or cold-start experiment:

## Findings and follow-up, in priority order

1. **Public backend abuse/availability risk (code confirmed):** no authentication, application rate limiter, request budget or cache; CORS is not abuse prevention.  Normal curl/non-browser callers can request supported rates and consume upstream/hosting capacity.  Review host limits, monitoring and a small rate limiter/cache before wider use.  No abuse was attempted and no fix was applied.
2. **On-device data risk (architecture confirmed):** names, money and saved details are plaintext localStorage readable by scripts on the same origin and by someone with browser-profile access.  GitHub Pages project paths on the same scheme/host share an origin; the app storage key is not isolation from other projects on that host.  A future XSS or compromised same-origin script could access trips despite replay masking.  Avoid sensitive records; consider a delete/export control, clear retention guidance and a separate origin for stronger isolation.  Current storage has no cloud backup, encryption, expiry or delete UI; quota/private mode/clearing data can lose history.  Concurrent tab writes are not coordinated.
3. **Third-party analytics and unverified fresh privacy evidence:** the SDK is dynamically loaded outside the lockfile; masking is configured, but a new playable replay and actual properties must still be reviewed after changes.  Dashboard retention/access/consent settings were not audited.  Review those settings and whether an opt-out/consent choice is appropriate for intended use.  Do not infer fresh funnel or replay verification from source tests.
4. **Cold-start/reliability and defensive bounds:** controlled Render Free sleep/wake retry behavior is pending; the frontend timeout may precede wake-up.  The backend bounds time, but does not explicitly cap upstream response-body size or add application concurrency limits.  `/health` does not establish Frankfurter availability.  Review these limits before wider traffic.  No exploit or failure was reproduced in this audit.
5. **Evidence/scope gaps:** Beginner screenshot eligibility awaits the actual assignment; history, binary screenshots and ignored private configuration were not scanned, and npm advisory results cannot cover unknown vulnerabilities or remote SDK code.  Secret and dependency scans should be repeated after changes.  No private credential was suspected in the scanned scope; no app fixes are claimed from this audit.
